# 02 · v2 总体方案：每一环的多方案对比与落地

> 对应作业要求：《大模型小组作业20261023设计.txt》第 1–3 条 + 最后一段"优化细化 plan、每个环节列举多个方案、针对用户设备优化"。
> 本文只讲**怎么做**与**为什么这样选**；接口与多端部署见 [03](03-接口连接与多设备.md)。

---

## 1. 设计原则

1. **真实优先**：宁可不抓，也不补造。没有来源链接和读取时间的活动，不进入时间表。
2. **可降级**：每条通道都有 Plan B。静态页失败→浏览器；浏览器失败→公众号/人工转发；模型失败→备用接口。
3. **可追溯**：原始页面、字段来源、抓取时间、置信度、复核状态全部落库。
4. **克制采集**：只读公开页、遵守 robots、限速、不登录他人账号、不抓私信。
5. **多端可用**：本机能用、手机能看、换电脑能继续，数据不锁死在一台机器。

## 2. 总体架构

```

│  对话页 index.html        招聘日历 /recruit        导出 ICS/CSV  │
│  模型设置（预设 / 体检 / 代理 / 备用链路）                       │
└───────────────▲──────────────────────────▲─────────────────────┘
                │ NDJSON 流                │ JSON / 文件
┌───────────────┴──────────────────────────┴─────────────────────┐
│                       应用层 server.mjs                         │
│  账号与租户 · 会话 · 聊天流 · 模型配置 · 体检 · 招聘 API         │
└──────▲───────────────▲──────────────▲───────────────▲──────────┘
       │               │              │               │
┌──────┴─────┐  ┌──────┴──────┐ ┌─────┴──────┐ ┌──────┴─────────┐
│ 智能体循环  │  │ 模型接入层   │ │ 招聘采集层  │ │ 平台浏览器     │
│ 规划→执行   │  │ 预设/代理/   │ │ 源注册/抓取 │ │ BOSS/小红书    │
│ →复核       │  │ 重试/流式/   │ │ /抽取/去重  │ │ （本人登录）   │
│ 工具调用    │  │ 体检/备用    │ │ /复核       │ │                │
└──────┬─────┘  └──────┬──────┘ └─────┬──────┘ └──────┬─────────┘
       │               │              │               │
┌──────┴───────────────┴──────────────┴───────────────┴─────────┐
│                          数据层                                │
│  SQLite：sources / events / raw_pages / runs                   │
```

**关键变化**：原项目是"对话 → 模型 → 回答"的单链；v2 是"对话 ↔ 数据 ↔ 采集"的闭环。模型可以**读取已经采集到的时间表**（`career_recruit_events`），采集结果也能反过来喂给对话做分析。

## 3. 数据模型（已落地）

```sql
sources(id, name, school, city, category, channel, list_url, mode, enabled,
        note, last_run, last_status, last_error, last_count)
events(id, source_id, school, city, kind, title, company,
       start_at, end_at, venue, address, industry, company_size,
       positions, requirements, apply_mode, apply_url,
       source_url, published_at, fetched_at, confidence, verified,
       raw_text, notes)
raw_pages(url, source_id, title, text, fetched_at, hash)
runs(id, source_id, started_at, finished_at, status, fetched, created,
     updated, message)
```

设计要点：

- `id = sha1(学校|标题|开始时间|地点)`：同一活动从不同来源抓到只会有一条。
- `confidence`（0–1）：字段越全越高；`verified`：用户点"复核来源"后为 1。
- `raw_text`：详情页原文片段，用于事后追责与二次抽取。
- `runs`：每次采集的成败与原因，界面可见——这是"真实有效"的审计线索。

### 4.2 多方案对比：怎么拿到"源"

| 方案 | 做法 | 成本 | 稳定性 | 合规风险 | 结论 |
| --- | --- | --- | --- | --- | --- |
| A. 静态 HTML | 直接 GET 列表页，正则/选择器解析 | 低 | 中（改版即失效） | 低 | **主力** |
| B. 隐藏 JSON 接口 | 从页面脚本里找 `postAjax` 地址，直接拿结构数据 | 低 | 高（字段全） | 低-中 | **优先发现** |
| C. 浏览器渲染 | Playwright 打开页面取 innerText | 中（慢、吃内存） | 中 | 低 | 兜底 |
| D. RSS / RSSHub | 订阅源 | 低 | 取决于自建服务 | 低 | 补充 |
| E. 微信公众号 | ①公众平台素材接口（需授权）②搜狗微信（验证码）③wechat2rss 自建（需扫码）④人工转发链接解析 | 高 | 低-中 | **高**（易违反平台条款） | **不做自动爬，做人工转发解析** |
| F. 第三方聚合 | 付费 API / 数据商 | 高 | 高 | 中 | 预算允许时 |

**本项目选择：B > A > C > D > E（人工）**。理由：B 一次适配长期稳定；A 覆盖最广；C 只对确实渲染的页面启用；E 的自动化风险与作业收益不成正比，改为"用户转发链接 → 智能体解析"，既合规又真实。

## 5. 环节二：抓取与反爬

### 5.1 多方案对比

| 方案 | 说明 | 成功要素 | 风险 |
| --- | --- | --- | --- |
| 浏览器 UA | 用常规 Chrome UA | 解决 90% 的 UA 封禁 | 需说明用途 |
| 限速 | 同域 ≥1.2s/次 | 避免触发风控 | 变慢 |
| robots.txt | 解析 Disallow 并遵守 | 合规底线 | 部分站点禁止则跳过 |
| 重试 + 退避 | 5xx/超时重试 2 次 | 抗抖动 | 无 |
| 代理池 | 换 IP | 应对 IP 限制 | 成本、合规、可靠性 |
| 浏览器指纹 | 真实浏览器渲染 | 应对 JS 校验 | 慢 |
| 官方接口/授权 | 走学校开放数据 | 最稳 | 通常不对外 |

### 5.2 本项目的降级链（已实现）

```
JSON 接口 → 静态 HTML → 浏览器渲染 → 报告"被拦截" → 建议公众号/人工转发 → 用户粘贴链接解析
```

每个源在 `sources.mjs` 里声明 `mode` 与 `fallback`；采集失败写入 `runs`，页面用红/灰标签展示，**不会把"没抓到"显示成"没有活动"**。

## 6. 环节三：结构化抽取

### 6.1 方案对比

| 方案 | 精度 | 成本 | 维护 | 适用 |
| --- | --- | --- | --- | --- |
| A. 纯规则（正则/选择器） | 中-高（字段固定时） | 低 | 改版要改 | 列表页、详情页固定模板 |
| B. 纯大模型抽取 | 高（字段乱时） | 中（每次调用） | 低 | 公众号文章、自由文本 |
| C. 规则 + 模型补全 | **高** | 中 | 中 | **推荐** |
| D. 人工校对 | 最高 | 高 | — | 关键场次 |

**本项目采用 C 的骨架**：规则负责"时间/地点/单位"这类强模式字段（已实测准确），模型负责"岗位要求/投递方式/活动流程"这类自由文本字段。每条记录保留 `raw_text`，可随时重跑抽取。

### 6.2 已实现的字段识别

| 字段 | 规则 | 效果 |
| --- | --- | --- |
| 开始/结束时间 | `2026-10-26【09:20:00-11:20:00】`、`时间：2026-11-13 14:00`、`14:00-17:00` | ✅ |
| 地点 | `地点：xxx`、列表第二列、`校区/楼/室/厅` | ✅ |
| 单位 | 列表"单位名称"列、详情"发布企业"、标题切分 | ✅ |
| 类型 | 标题关键词（双选会/宣讲/培训/招聘公告） | ✅ |
| 城市 | `浙江省杭州市 → 杭州` 归一化 | ✅ |
| 行业/规模 | 上财接口自带 `hyyjmc` / `rsgmmc` | ✅ |
| 网申/投递 | 详情页关键词（报名/投递/网申/邮箱） | 规则待补，可由模型补 |

## 7. 环节四：真实性校验（作业 1.3.2）

### 7.1 方案对比

| 方案 | 能解决 | 不能解决 | 成本 |

## 8. 环节五：排班与行程（作业 2.3）

### 8.1 方案对比

| 方案 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 自研冲突检测 | 时间区间重叠 + 同城判定 | 零依赖、可控 | 通勤靠估算 |
| B. 地图 API（高德/百度/腾讯） | 实时路径与耗时 | 准 | 要 Key、有配额、有商用限制 |
| C. 日历导入（ICS） | 交给系统日历/导航 | 生态好 | 不在应用内 |
| D. 手工排 | 人判断 | 灵活 | 不自动 |

**本项目：A + C 已实现，B 预留接口**。生成的 ICS 可以直接导入手机日历（iOS/Android/Outlook），到点提醒、点地址跳地图——这是"用户设备优化"最省力的做法。

### 8.2 已实现的规则

- 同日、同城、时间重叠 → `时间冲突`（红色）
- 同日、同城、间隔 < 估算通勤 → `赶场风险`（橙色）
- 同日、异地 → `需取舍或改天`（不算冲突，避免误报）
- 通勤估算：校区坐标直线距离 × 1.35 / 25km/h + 15 分钟缓冲；跨城固定 180 分钟
- 导出：`.ics`（日历）、`.csv`（Excel）、`.md`（打印/交作业）

> 实测数据里，10-23 当天同时有成都和上海的场次，系统正确标记为"同日异地"而不是"时间冲突"。

## 12. 设备与多端（详见 03）

一句话结论：

- **短途（同 Wi-Fi）**：局域网模式，手机直接看日历。
- **异地（回家/实习）**：Tailscale 私有组网，不暴露公网。
- **小组共用**：一台云服务器 + HTTPS + 账号隔离；浏览器类工具仍留在本人电脑。
- **不想运维**：只把"日历 + 采集结果"做成只读站点，模型能力留在本机。
