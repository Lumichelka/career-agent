## 2. WorkMaster：把"高校招聘日历"这件事做透了

项目：<https://github.com/chidou59/workmaster>

### 2.1 它做了什么

- 覆盖南京、上海、苏州及周边 **33 所高校**的宣讲会/招聘会；
- 服务器定时采集（默认 **30 分钟**增量同步），所有访问者共享同一份数据；
- 七列月历、按时间排序、时间待定单列、密集日期折叠；
- 支持城市/学校/类型/线上线下/状态/关键词筛选；
- 详情页保留学校原文链接、结构化岗位、参展企业；
- **33 个来源的健康状态**可见；单源失败不影响其他源；
- 活动连续三次从成功响应中消失 → 标记"**可能撤下**"；取消活动保留不删除；
- SQLite + WAL + FTS5；海报岗位用 OCR 提取并标注"需核对"；
- 只绑定 `127.0.0.1`；Docker/宝塔部署；桌面版数据放 `%LOCALAPPDATA%`。

### 2.2 我们该借的

| 做法 | 为什么 | 落到 v3 |
| --- | --- | --- |
| 源健康面板 | 失败可见，才谈得上"渠道通畅" | 已有雏形，P2 做成独立面板 |
| 活动生命周期 | "没抓到"≠"取消了" | 新增 `status`：active/cancelled/possibly_removed |
| 去重键含来源 | 同企业在不同学校是两场活动 | 现有 `school+title+time+venue` 已符合 |
| 字段缺失显示"来源未提供" | 不推测 | 已在采集层做，UI 需统一 |
| FTS5 搜索 | 活动多了以后很好用 | P2 加 `events_fts` |
| 数据放 `%LOCALAPPDATA%` | 代码干净、隐私安全 | Phase 0 执行 |
| 定时增量同步 | 保持新鲜 | P2 加调度器 |

### 2.3 我们不该照搬的

- 33 校全量覆盖：我们聚焦四川 + 财经强校，先深后广；
- 共享一份数据：我们要账号隔离；
- OCR 海报：P3 以后再说，先保证文本源质量。

## 3. 录阶 LuJie CareerKit：把"求职流程"做成了工作台

项目：<https://github.com/Chozzc/Lujie-Careerkit>

### 3.1 它做了什么

- **简历版本**：多份简历、独立副本、模板主题、导出 PDF/PNG/DOCX；
- **AI 分析简历**：先诊断问题，用户选择方向，再生成独立优化版本，保留原稿；
- **JD 匹配**：粘贴完整 JD → 诊断匹配点/缺口 → 重排重点 → 保存岗位定制版；
- **面试准备**：资料概览、能力画像、证据与差距、核心知识、经历深挖、针对性问题、准备计划；
- **模拟面试与复盘**：逐题回答、AI 点评、可回看；
- **投递跟进看板**：公司/岗位/渠道/阶段/截止/跟进日期/备注/JD/绑定简历；
- **校招信息库**：关键词/类型/届别/地点筛选；
- **应用内 Agent**：检索校招、读简历、创建版本、生成面试资料；**所有业务写入都要用户确认**；
- **Agent Skills**：把简历优化、面试准备、模拟面试、求职沟通做成 4 个 `SKILL.md`，Codex/Claude Code 可直接用；
- 数据本地 SQLite，API Key 加密，Agent 读简历时过滤邮箱电话。

### 3.2 我们该借的

| 做法 | 落到 v3 |
| --- | --- |
| Skill 作为目录（SKILL.md + 约束 + 验收） | `src/skills/` 四个技能包 |
| 写操作先预览再确认 | 简历/投递/记忆写入的硬规则 |
| 简历多版本、一岗一版 | `resumes` / `resume_versions` 表 |
| 投递看板 | `applications` 表 + 页面 |
| 读简历时脱敏 | 工具层过滤联系方式 |
| 导出 DOCX | P3（当前只有 txt） |

### 3.3 我们不照搬的

- 它没有"高校线下招聘采集"，这是我们的差异点；
- 它偏"投递后管理"，我们偏"投递前发现机会"；
- 它的在线预览存浏览器，我们坚持本地数据。

## 5. 差距分析：我们在哪、别人在哪

| 能力 | 我们 v2 | WorkMaster | 录阶 | v3 目标 |
| --- | --- | --- | --- | --- |
| 高校线下活动采集 | ✅ 7 源 / 121 场 | ✅ 33 校 | ❌（有校招库但非线下日历） | ≥12 源 |
| 活动生命周期 | ❌ | ✅ | — | P1 |
| 源健康面板 | 半成品 | ✅ | — | P2 |
| 简历版本/JD 匹配 | 只有文稿 | — | ✅ | P3 |
| 投递跟进 | ❌ | — | ✅ | P3 |
| 面试模拟 | ❌ | — | ✅ | P3 |
| Agent 工具/技能 | 工具有，技能无 | — | ✅ Skills | P1/P3 |
| 记忆分层 | 只有会话 | — | 部分 | P3 |
| 本地优先/隐私 | ✅ | ✅ | ✅ | ✅ |
| 多端 | 局域网 | 桌面版/服务器 | Docker | P4 |

**结论**：我们不需要变成 WorkMaster 或录阶；我们的差异点是 **"四川/财经高校的线下招聘 + 可执行的行程 + 求职材料闭环"**。借它们的工程做法，不借它们的范围。

---

## 6. 调研直接改变了哪些设计

1. **活动状态**：从"只有 verified"改为 `active/cancelled/possibly_removed`（借 WorkMaster）。
2. **技能目录化**：不把提示词写死在 `agent.mjs`，改成 `skills/*/SKILL.md`（借录阶）。
3. **写操作确认**：简历/投递/记忆写入必须预览确认（借录阶）。
4. **数据外置**：`%LOCALAPPDATA%`，代码与数据分离（借 WorkMaster 桌面版）。
5. **源健康面板**：独立页面，而不是一行日志（借 WorkMaster）。
6. **FTS5 搜索**：活动量上来后必备（借 WorkMaster）。
7. **不自动投递**：两家都没做，行业也没有可靠方案，保持边界。
