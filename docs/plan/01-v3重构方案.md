# 01 · v3 重构方案（详细计划）

> 这份方案先解决"为什么乱"，再定义"做成什么样"，最后给出"分几步做"。
> **在你确认之前，我不会移动代码、不改现有功能**；本阶段只产出方案与版本控制基线。

---

## 1. 产品定义（先统一目标）

现在这个项目更像"一个会聊天的网页 + 一个采集脚本"。
v3 要把它定义成：

> **一个本地优先的求职自动化工作台**：
> 每天自动收集目标高校的线下招聘 → 整理成可信的日程 → 结合你的简历和岗位，产出投递材料与面试准备 → 全过程可追溯、可由你确认。

三条主线，对应作业的三块要求：

```
信息线：信息源 → 采集 → 抽取 → 校验 → 活动库 → 日历/行程
匹配线：我的画像/简历 → 岗位要求 → 差距分析 → 定向材料 → 面试准备
任务线：自然语言 → 计划 → 工具调用 → 交付 → 记忆
```

---

## 2. 设计原则（用来判断"该不该做"）

1. **一条主路径 ≤ 3 步**：用户不该为了看一场宣讲会点五次。
2. **能力可见**：有哪些工具、哪些技能、记住了什么，界面上能查到（对应你的疑问）。
3. **数据与代码分离**：代码进 git，数据进用户目录，互不污染。
4. **真实优先**：没有来源和抓取时间的活动不进日历；模型不许编造经历。
5. **写入要确认**：改简历、记投递、改日程，默认先给预览再落库。
6. **可回退**：每个阶段一个 git 提交/标签，坏了一眼能回滚。

## 6. 智能体设计（回答"tool / skill / memory"）

### 6.1 循环

```
① 理解：这轮要做什么？缺什么信息？
② 计划：1–5 步，给用户看
③ 执行：选工具（只读优先）；需要写操作时先预览
④ 交付：回答 / 文稿 / 表格 / 日历
⑤ 复核：来源、事实、用户约束
⑥ 记忆：只把"用户确认过"的写进长期记忆
```

### 6.2 工具（Tools）——模型能"动手"的接口

统一注册，每个工具有：名称、说明、参数 schema、权限（read/write）、超时、失败返回。

| 工具 | 权限 | 作用 |
| --- | --- | --- |
| `recruit.query` | read | 查询本机活动库（城市/时间/学校/类型） |
| `recruit.refresh` | write(内部) | 触发采集 |
| `recruit.schedule` | read | 排班、冲突、导出 |
| `search.public` | read | SearXNG 公开搜索 |
| `company.research` | read | 公司公开信息简报 |
| `platform.status/search/read` | read | BOSS/小红书（本人登录） |
| `resume.list/get` | read | 读取简历版本 |
| `resume.save_version` | **write** | 保存新版本（需确认） |
| `application.upsert` | **write** | 投递记录（需确认） |
| `memory.read/write` | read/write | 记忆（写入需确认） |

> 现在这些定义分散在 `api-model.mjs`、`tool-policy.mjs`、`platform-mcp.mjs` 三处，v3 合并为一份注册表，并生成"能力面板"给你看。

### 6.3 技能（Skills）——可复用的"办事流程"

技能不是工具，而是**怎么组合工具、按什么步骤、产出什么格式**。

| 技能 | 触发 | 步骤 | 产出 |
| --- | --- | --- | --- |
| `schedule-planner` | "帮我排行程/这周有什么" | 查活动 → 去重 → 冲突 → 通勤 → 输出 | 日程表 + ICS |
| `company-research` | "这家公司怎么样" | 搜索 → 交叉 → 结构化 → 标注局限 | 公司简报 |
| `resume-tailoring` | "按这个 JD 改简历" | 读简历 → 拆 JD → 证据映射 → 改写 → 差异 | 新版本 + 缺口清单 |
| `interview-prep` | "准备面试" | 流程预测 → 题库 → 追问 → 复盘 | 面经 + 练习题 |

每个技能一个目录：`SKILL.md`（做什么/何时用）、`prompt.md`（约束）、`schema.json`（输出）、`checklist.md`（验收）。

### 6.4 记忆（Memory）——三层，而不是一段字符串

| 层 | 存什么 | 存哪 | 谁能改 |
| --- | --- | --- | --- |
| L1 会话记忆 | 当前对话确认的事实 | `session.memory`（现有） | 每轮自动 |
| L2 长期画像 | 专业、届别、城市偏好、技能标签、经历要点 | `data/profile.json` | 用户确认后写；面板可删 |
| L3 任务记忆 | 计划、工具证据、产物 | 任务记录 | 自动，可追溯 |

规则：**没被用户确认的不进 L2；联系方式、证件号、平台密码永不入记忆。**

### 6.5 护栏

- 没有来源的招聘事实不输出；
- 简历数字只能来自用户素材；
- 写操作先预览后落库；
- 不自动投递、不发消息、不碰验证码。

## 11. 风险与取舍

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 高校站点反爬/改版 | 采集中断 | 适配器隔离 + 健康度 + 浏览器兜底 + 人工转发 |
| 公众号自动化违规 | 账号风险 | 只做链接解析/自建 RSS，不模拟登录 |
| 模型编造 | 简历/公司信息失真 | 来源强制 + 证据映射 + 复核 |
| 数据隐私 | 简历/账号泄露 | 数据外置 + 不进 git + 加密 Key |
| 范围过大 | 做不完 | 按 Phase 交付，每阶段可停 |
| 迁移破坏现有功能 | 无法使用 | git 标签 + 迁移脚本 + 测试门禁 |

**明确不做**：自动投递、自动发消息、抓取验证码、爬取私信、云端多租户商业化。

## 12. 与原框架的取舍

| 原模块 | v3 处置 | 理由 |
| --- | --- | --- |
| 账号/租户/Key 加密 | **保留** | 设计正确，只需换数据目录 |
