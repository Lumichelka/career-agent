# AI 来源操作员：允许在应用 profile 中执行任意 Playwright/JS

## 状态

accepted（2026-10-27）

## 背景

央财、对外经贸、西南财大、24365/国聘等来源无法用固定解析器稳定采集：有的被 banner 覆盖，有的需要登录，有的 robots 禁止代码抓取。用户要求让接入的 AI 在浏览器里代替硬编码采集，并明确选择“完整 Agent + 任意 Playwright 动作/JS”，登录态保存在应用自己的 persistent profile。

## 决策

- 来源操作使用应用内本地浏览器操作员，per-user 一个 persistent profile；用户首次在可见窗口登录，登录态只存在 profile，不提取 cookie/密码。
- 允许任意 Playwright 动作与 page.evaluate JS；不把提示词当安全边界。
- 每次运行必须：用户手动触发、可见窗口、单次确认、可随时停止。
- 唯一硬上限：单次运行 <10 分钟；不限制列表/详情数量、翻页、步数或模型成本。
- 触到登录/验证码/异常/时间上限：暂停任务，转人工接管；用户处理后可从未完成步骤继续，不把任务判失败。
- 禁止 file://、chrome://、edge://、localhost、私网；禁止下载/上传；允许剪贴板。
- 对“投递/支付/删除/退出/提交表单”做尽力而为的硬确认（按钮文本/表单提交/下载事件命中即暂停）；文档明确不承诺防任意 JS 绕过。
- 每源一个 playbook 文件，写入口、允许域、成功标志、禁止动作与抽取提示；playbook 是可评审的源知识，不是秘密提示词。
- 仅支持单用户本机；不做多用户/远程。后续若要多用户/远程，必须先改为受限沙箱（C-lite）。

## 考虑过的替代

- **C-lite**：完整动作集但硬限制域名、禁止读存储/跨域网络/危险动作。更安全，但用户明确要求任意 JS 与跟随新页面。
- **固定脚本 + AI 只抽取**：无法处理 banner/登录/结构变化，不符合“AI 代采集”目标。

## 后果

- profile 可能持有真实账号登录态；恶意页面或 prompt injection 可诱导 Agent 读取页面内存储、发同源请求或点击危险按钮。这是已接受的风险，不是安全隔离。
- 必须保留动作日志与关键截图；没有它们无法复盘 AI 做了什么。
- 对外/多用户前必须重新评估；当前设计不能直接暴露给其他用户或远程调用。

## 验证记录（2026-10-27，本机 Edge 150）

- 对外经贸：首页、Menu → 就业 → 招聘活动列表、活动详情均公开可读；列表每页 20 条、共 202 页；详情含单位/地点/时间/正文。**不需要登录，结构可被代码解析**，不是 AI 操作员的理想难源。
- 西南财大：列表公开、结构可读；页面有 Tencent 验证码 iframe 但未阻断浏览。应用内 Playwright Edge 的 source-check 真实链路跑通：任务成功、13 条写入、4 项证据、截图 2 张；外部 Agent 复核因未配置而不可用。验证后已把 recruit.db/wechat.db 恢复为验证前备份。
- 24365：首页公开、职位/活动列表结构可读；登录只影响投递等动作，不影响首页浏览。
- 结论：UIBE / SWUFE / 24365 的公开页都可以用代码或既有 source-check 覆盖，不能证明“AI 操作员”的必要性。真正需要 AI 的是**登录后平台**（BOSS/实习僧/牛客/智联/51job/猎聘）与**公众号文章列表/验证**。机制原型源需要重新选择。
